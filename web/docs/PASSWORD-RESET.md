# 이메일 발송 설정과 비밀번호 재설정 · 0.18.0

로그인 화면의 **비밀번호를 잊으셨나요? → 가입 이메일 입력 → 재설정 메일 보내기**를 사용합니다. 이메일 링크에서 새 비밀번호와 확인값을 입력한 뒤 다시 로그인하세요. 관리자 계정의 인증 앱·복구 코드는 유지됩니다. SSO·AD 전용 계정은 회사 인증 서비스에서 비밀번호를 변경하세요.

## 관리자 화면에서 설정하기

관리자 계정으로 로그인한 뒤 **계정 → 관리자 설정 → 메일**을 엽니다.

1. 이메일 발송 사용을 켭니다.
2. SMTP 서버, 포트, 보안 연결, 발신 이메일을 입력합니다. 일반적으로 587번은 STARTTLS, 465번은 TLS를 사용합니다. 연결 방식을 고르면 기본 포트를 제안하며 사용자 지정 포트도 입력할 수 있습니다.
3. SMTP 인증을 사용하는 서버라면 인증 계정과 비밀번호를 입력합니다. 인증 없는 사내 TLS 릴레이는 SMTP 인증 사용을 끕니다.
4. **설정 저장**을 누릅니다. 재기동 없이 다음 메일부터 적용하며 서버를 재시작해도 유지합니다.
5. 받는 이메일을 확인하고 **테스트 메일 보내기**를 누릅니다. 기본 수신자는 현재 관리자 이메일입니다. SMTP 서버가 수락하면 받은 편지함·스팸함에서 실제 도착 여부를 확인하세요.

테스트는 저장된 설정으로 실행합니다. 입력을 바꾸면 먼저 저장해야 테스트할 수 있습니다. SMTP 서버 수락은 받은 편지함 도착을 보장하지 않으므로 발송 서비스의 도메인·수신 정책도 확인하세요. 인증 실패와 보안 연결·주소·포트 문제를 화면에 안내하며 서버가 반환한 원문에 비밀번호가 포함되더라도 표시하지 않습니다.

등록한 비밀번호는 화면/API에서 읽을 수 없습니다. 빈칸으로 저장하면 기존 값을 유지합니다. 서버 주소나 인증 계정을 바꿀 때는 비밀번호를 다시 입력하세요. SMTP 인증을 끄고 저장하면 등록된 인증 계정·비밀번호를 삭제합니다. 이메일 발송만 중지하면 나중에 다시 켤 수 있도록 인증 정보는 유지합니다.

두 관리자가 동시에 수정하면 먼저 저장한 설정을 유지하고 늦은 요청은 충돌로 안내합니다. 설정 화면을 다시 열어 최신 값을 확인한 후 수정하세요. 일반 사용자에게는 메뉴를 표시하지 않고 API도 거절합니다. 저장·발송에는 관리자 로그인과 CSRF 검사가 필요합니다. 설정 저장은 관리자당 20회/10분, 테스트는 관리자당 5회/10분·전체 20회/10분, 동시 SMTP 발송은 프로세스당 2개로 제한합니다.

관리자 화면의 설정은 DB에 저장하며 파일 설정보다 우선합니다. SMTP 비밀번호는 MFA 키에서 용도를 분리해 파생한 키로 AES-256-GCM 암호화합니다. DB 백업과 별도로 **config/secrets/mfa.key**를 보관해야 복원 후 인증 정보를 읽을 수 있습니다. 복원 후 테스트 메일로 설정을 확인하세요. 설정 변경·테스트 발송 성공/실패는 보안 감사 로그에 기록하며 비밀번호는 포함하지 않습니다.

같은 SMTP 설정을 [회원가입 이메일 인증·관리자 승인 요청·승인 안내](REGISTRATION.md)에도 사용합니다. 발송을 중지하면 신규 가입 신청·인증 메일 재발송도 중지됩니다. 이미 받은 인증 링크는 만료 전까지 사용할 수 있습니다.

## 승인 요청 수신 이메일

같은 설정 화면의 **승인 요청 수신 이메일**에 하나 이상의 이메일을 입력합니다. 쉼표·줄바꿈으로 최대 10개까지 지정할 수 있고, 비워두면 활성 관리자들의 등록 이메일을 사용합니다. 저장 후 현재 승인 대기 신청에도 적용하며, 이미 같은 주소에 전달한 요청은 중복 발송하지 않습니다. 수신자별로 개별 발송하며 가입 승인 권한은 관리자 계정에만 있습니다.

이 설정은 관리자 승인 요청 메일에만 적용합니다. 회원가입 인증·비밀번호 재설정·가입 승인 결과 메일은 해당 사용자의 이메일로 보냅니다. SMTP 비밀번호 입력란은 비워두어 기존 값을 유지할 수 있습니다.

파일 설정만 사용하는 경우 mail.json의 reviewRecipients 배열에 주소를 넣을 수 있습니다. 기본값은 빈 배열이며, 관리자 화면에 저장하면 DB 설정이 우선합니다.

## 파일로 SMTP 설정하기

실제 발송에는 운영자가 제공한 SMTP 서버와 계정이 필요합니다. 현재 작업 폴더에는 비활성 상태의 **config/mail.json**과 비밀번호를 넣을 빈 **config/secrets/smtp-password.txt**를 준비했습니다. 새 설치는 config/mail.example.json을 config/mail.json으로 복사하세요.

설정 파일의 enabled를 true로 바꾸고 host, port, secure, from, username을 채웁니다. 기본 예제는 587번·STARTTLS입니다. secure=false여도 반드시 TLS로 업그레이드하며 인증서를 검증합니다. 465번의 처음부터 TLS 방식은 secure=true로 설정하세요. 평문 SMTP·인증서 검증 생략은 지원하지 않습니다.

passwordFile은 mail.json을 기준으로 한 상대 경로입니다. 기본값 **secrets/smtp-password.txt**라면 **config/secrets/smtp-password.txt**를 텍스트 편집기로 만들고 SMTP 비밀번호 또는 발송 서비스의 앱 비밀번호를 한 줄로 저장하세요. 파일 권한은 운영 계정만 읽도록 제한합니다. 인증 없는 사내 TLS 릴레이는 username과 passwordFile을 모두 빈 문자열로 설정합니다.

from은 실제 발신 권한이 있는 이메일 주소를 지정하세요. SMTP 서비스의 발송 허용·발신 도메인 설정도 해당 서비스에서 준비해야 합니다. 사설 CA는 기존 NODE_EXTRA_CA_CERTS 설정으로 신뢰 인증서를 지정할 수 있습니다.

설정 예제:

    {
      "enabled": true,
      "host": "smtp.example.com",
      "port": 587,
      "secure": false,
      "from": "pmcanvas@example.com",
      "username": "pmcanvas@example.com",
      "passwordFile": "secrets/smtp-password.txt"
    }

**PUBLIC_ORIGIN은 수신자가 접속할 수 있는 앱의 실제 HTTPS 주소로 설정하세요.** localhost 링크는 수신자의 컴퓨터에서 같은 앱에 접속할 수 있을 때만 동작합니다. BASE_PATH는 링크에 자동 반영됩니다. 요청의 Host 헤더로 링크를 만들지 않습니다.

파일 설정은 관리자 화면에서 아직 설정을 저장하지 않은 경우 적용됩니다. 화면에 한 번 저장한 뒤에는 화면에서 관리하세요. 파일 변경을 적용하려면 앱을 다시 기동합니다.

기본·외부 DB Compose 구성은 `MAIL_CONFIG_DIR=/app/config`로 마운트한 `mail.json`을 읽습니다. 파일이 없는 새 설치도 정상 기동하며 메일은 비활성화됩니다. Docker 없이 실행하면 기존 `config/mail.json`을 사용하고, `MAIL_CONFIG_FILE`을 지정하면 기본 디렉터리보다 우선합니다.

    npm run service:up
    docker compose exec app node scripts/check-mail.mjs

이 명령은 **파일의 SMTP 설정만** 검사합니다. 관리자 화면에 저장한 설정은 화면의 테스트 메일을 사용하세요. 파일 확인 명령은 SMTP 연결·TLS·인증만 검사하며 메일을 보내지 않습니다. Docker 없이 실행하면 **npm run mail:check**를 사용하세요. MAIL_CONFIG_FILE을 지정하면 다른 설정 파일도 사용할 수 있습니다. Docker 경로는 /app/config/mail.json과 같이 컨테이너 기준으로 지정합니다. 외부 DB 구성에서도 같은 설정을 사용합니다.

실제 비밀번호·운영 mail.json은 Git·설치 ZIP에서 제외됩니다. 비밀 파일을 예제 파일에 넣지 마세요.

## 링크와 계정 보호

- 무작위 256비트 토큰의 SHA-256 해시만 DB에 보관하고 15분 후 만료합니다. 새 링크를 발급하면 이전 링크는 무효화합니다.
- 토큰은 URL 프래그먼트에 넣어 서버 요청 URL에 포함되지 않게 하고, 화면이 읽는 즉시 주소창에서 제거합니다. Referrer-Policy도 no-referrer로 설정합니다. 새로고침으로 링크가 사라졌으면 이메일에서 다시 여세요.
- 비밀번호 변경·토큰 소비·세션 삭제를 한 DB 트랜잭션으로 처리합니다. 동시 요청도 한 번만 성공합니다. 정상 변경 뒤에는 자동 로그인하지 않습니다.
- 현재 비밀번호 해시와 토큰을 함께 묶어 이전 비밀번호의 링크를 사용할 수 없게 합니다. 비밀번호 변경·관리자 초기화·계정 비활성화도 링크를 폐기합니다.
- 관리자 MFA는 유지하고 이전 비밀번호에 묶인 MFA 로그인 요청은 무효화합니다. 비밀번호 재설정은 MFA 복구를 대신하지 않습니다.
- 이메일 존재·외부 인증·비활성·가입 대기 여부와 관계없이 같은 접수 응답을 보냅니다. 발송은 제한된 별도 비동기 작업으로 처리합니다. 외부·비활성·가입 대기 계정에는 메일을 보내지 않습니다.
- 요청은 이메일별 3회/시간, 검증된 IP별 10회/15분, 전체 100회/시간으로 제한합니다. 링크 사용도 IP·전체·토큰별 제한을 적용합니다. 성공한 재설정은 해당 계정의 기존 로그인 시도 제한을 해제합니다.
- 링크·비밀번호·SMTP 비밀번호는 앱 로그와 API 응답에 기록하지 않습니다. 메일 발송·실패·변경 완료는 보안 감사 로그에서 확인합니다.

발송 대기열은 현재 프로세스의 메모리에 보관합니다. 재기동·메일 장애로 수신하지 못했다면 다시 요청하세요. 발송 실패 시 해당 링크를 폐기합니다. 사용 가능한 설정이 없으면 발송 기능을 비활성으로 표시하며 성공했다고 안내하지 않습니다.

DB 복원 명령은 기존 재설정 링크도 폐기합니다. 007_password_reset 마이그레이션은 앱 시작 시 자동 적용합니다. 업데이트 전 DB를 백업하세요.

구현 참고: [OWASP 비밀번호 찾기 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [Nodemailer SMTP 설정](https://nodemailer.com/smtp).

008_mail_settings 마이그레이션은 시작 시 자동 적용합니다. 기존 파일·비밀 파일은 수정하지 않으며 첫 화면 저장 때 유효한 기존 비밀번호를 암호화해 DB로 가져옵니다.
