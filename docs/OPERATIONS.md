# 운영 화면 · 내 업무 · 휴지통 · 자동 백업 (0.18.0)

## 관리자 설정과 가입 처리

계정 → 관리자 설정에 가입 승인·사용자·메일·인증·보안·백업을 모았습니다. 가입 승인에서는 이메일 인증 완료와 인증 대기를 구분하고, 사용자에서는 활성·비활성·거절 계정을 필터링합니다. 이름·이메일로 검색할 수 있으며 계정 버튼에 승인 대기 수가 표시됩니다.

신청 검토에서 계정과 소속을 확인한 뒤 승인하거나 거절합니다. 이메일 인증 전에는 거절만 할 수 있습니다. 승인할 때 내가 소유한 프로젝트와 편집자·조회자 권한을 선택할 수 있으며 계정 승인·권한 부여·승인 안내 메일 작업을 같은 트랜잭션으로 저장합니다. 하나라도 실패하면 모두 취소합니다. 관리자는 자신에게 공유 권한이 없는 다른 소유자의 프로젝트에 권한을 줄 수 없습니다. 거절 사유는 관리자 기록용이며 거절 계정은 활성화하거나 로그인할 수 없습니다.

계정 직접 추가·일반 계정 활성화/비활성화·비밀번호 초기화는 사용자 탭에 있습니다. SSO 설정과 보안 감사 로그는 인증·보안 탭에서 엽니다. SMTP와 승인 요청 수신 주소는 메일 탭에서 설정합니다.

## 내 업무

프로젝트 소유자가 **프로젝트 한눈에 → 프로젝트 관리 → 공유 → 참여인력과 계정 연결**에서 담당자와 로그인 계정을 연결합니다. 먼저 해당 계정을 프로젝트에 공유해야 합니다. 프로젝트마다 계정 하나와 참여인력 하나를 일대일로 연결하며 이름이나 이메일을 추측해 자동 연결하지 않습니다.

**내 업무**에서 연결된 모든 프로젝트의 지연·진행 일정·예정·완료 업무를 봅니다. 업무 카드를 누르면 해당 프로젝트의 완료 체크로 이동합니다. **이 프로젝트 완료 체크**로 직접 전환해 기존 담당자 필터·기준일·체크 기능을 사용할 수도 있습니다. 조회자는 확인만 가능합니다. 인력 삭제나 공유 해제 시 연결도 제거합니다. 계정 비활성화는 로그인 자체를 차단하고 재활성화하면 보존된 공유와 연결을 다시 사용합니다.

## 휴지통

프로젝트 관리 → 설정의 프로젝트 삭제는 소유자만 가능합니다. 업무는 기존 상세 편집 또는 WBS에서 삭제합니다. WBS 초안의 삭제는 **저장한 시점**부터 휴지통에 기록됩니다. 초안 취소는 삭제를 서버에 반영하지 않습니다.

파일 → 휴지통에서 프로젝트는 소유자가, 업무는 현재 편집 권한이 있는 사용자가 복구합니다. 삭제된 프로젝트는 공유 사용자에게도 보이지 않고 API 접근도 차단합니다. 프로젝트를 복구하면 기존 공유·참여인력·업무·완료 기록이 돌아옵니다. 프로젝트가 삭제된 동안 그 안의 업무 휴지통은 별도 노출하지 않습니다.

업무 복구는 원래 ID·세부 작업·완료일·일정·가능한 연결을 되살리며 삭제 후 남은 업무에 입력한 내용을 보존합니다. 담당자·선행·상위 업무가 사라졌으면 연결을 해제하고 알려줍니다. 같은 ID가 이미 있거나 연결이 현재 데이터와 충돌하면 복구를 중단하고 기존 내용을 보존합니다. 복구한 프로젝트의 revision이 증가하므로 이전 화면에서 저장하면 충돌 안내를 받습니다.

삭제 후 30일이 지나면 복구할 수 없습니다. 앱 시작·시간당 정리·휴지통 조회 때 만료 데이터를 실제 삭제합니다. 세부 체크 항목과 참여인력만 삭제한 경우는 휴지통 대상이 아닙니다. 이 경우 변경 이력 또는 전체 DB 백업을 참고하세요.

## 자동 DB 백업

기본 compose.yml은 앱·DB와 함께 **backup** 서비스를 시작합니다. 관리자 설정 → 백업에서 다음을 설정합니다.

- 매일 자동 실행 여부, 실행 시각(한국 표준시, 0–23시), 자동 덤프 보관 기간(1–365일).
- 백업 후 실제 복원 점검 여부. 켜면 임시 DB를 만들고 덤프 복원·스키마·참조 검사를 수행한 뒤 그 임시 DB만 삭제합니다. 운영 DB를 덮어쓰거나 복원한 앱을 실행하지 않습니다.
- 지금 백업 요청, 최근 20회 결과, 마지막 성공과 복원 점검 시각, 작업 서비스 연결 상태. 요청은 최대 30초 후 작업 서비스가 가져갑니다. 요청 중복과 동시 실행은 DB lease로 막습니다.

첫 기동 기본값은 자동 실행 켜짐, 매일 03시, 14일 보관, 복원 점검 켜짐이며 최초 백업도 한 번 실행합니다. 설정 저장 시 다음 자동 시각을 계산합니다. 자동 실행을 꺼도 지금 백업을 요청할 수 있습니다. 설정 충돌 시 최신 화면을 다시 여세요. 실패에는 실패한 단계만 표시하며 DB 비밀번호와 원문 오류는 표시하지 않습니다.

백업 파일은 호스트의 **backups/pmcanvas-auto-….dump**, 암호화 키 사본은 **backups/keys/key-해시.bin**에 저장합니다. 키는 관리자 MFA와 SMTP 비밀번호 복원에 필요합니다. **backups 전체를 비공개로 보관하고 다른 서버나 저장소에도 복사하세요.** 이 기능은 같은 호스트에 저장하므로 호스트 자체 손실에 대한 외부 사본을 대신하지 않습니다. 자동 정리는 이름이 일치하는 일반 자동 덤프 파일에만 적용하고 수동 덤프·키는 삭제하지 않습니다. 실제 파일 목록 확인은 서버 운영자가 수행하며 앱에서 덤프와 비밀 키를 내려받는 기능은 제공하지 않습니다.

백업 서비스만 DB 운영 자격 증명을 사용합니다. 앱 컨테이너에는 DB 관리자 암호나 Docker 소켓을 주지 않습니다. 백업 서비스는 네트워크 포트를 공개하지 않으며 읽기 전용 루트·제한된 기능·전용 쓰기 디렉터리로 실행합니다. Linux에서는 호스트 backups 디렉터리와 키 파일을 컨테이너 UID/GID 1000이 사용할 수 있도록 권한을 설정하세요.

## 복구 절차

기존 수동 백업과 복원 명령도 사용할 수 있습니다.

```sh
npm run backup
npm run restore -- backups/pmcanvas-auto-파일.dump pmcanvas_restore_check
```

restore는 새 DB에만 복원하고 기존 DB를 덮어쓰지 않습니다. 복원 시 세션·인증 챌린지·비밀번호 재설정·가입 인증 링크를 제거하고 MFA 복구 코드를 무효화합니다. 앱을 연결하기 전에 내용을 확인하세요. 보관한 같은 암호화 키를 config/secrets/mfa.key에 복원해야 기존 인증 앱과 SMTP 설정을 사용할 수 있습니다. 원래 키를 잃었다면 운영자 MFA 초기화와 SMTP 자격 증명 재설정이 필요합니다. APP_DATABASE를 복원 DB 이름으로 바꿔 서비스 기동 후 로그인과 데이터를 확인하세요. 실패한 수동 복원 DB의 정리는 운영자가 수행합니다.

## 외부 PostgreSQL과 직접 실행

외부 DB에서는 운영 계정이 전체 DB를 읽고 CREATEDB 및 앱 역할로 SET ROLE 할 수 있어야 복원 점검까지 가능합니다. `.env`에 BACKUP_PGUSER·BACKUP_PGPASSWORD를 비공개로 설정합니다. PGHOST·PGPORT·PGDATABASE·PGSSLMODE·PGSSLROOTCERT는 기존 외부 DB 설정을 사용합니다. PostgreSQL 18 클라이언트 이미지이므로 그보다 최신 서버는 해당 버전에 맞게 이미지를 조정해야 합니다.

```sh
docker compose -f compose.external.yml --profile backups up -d --build
```

외부 DB 운영 정책상 새 DB 생성을 허용하지 않으면 복원 점검을 끄고 별도 승인된 환경에서 주기적으로 복원을 확인하세요. 파일만 검사한 결과에는 ‘복원 점검 통과’를 표시하지 않습니다. 외부 DB 자동 백업도 backups와 같은 MFA 키 파일을 사용합니다. 이 디렉터리는 시작 전에 만들어 두세요.

Node.js만 직접 실행하는 환경은 pg_dump·pg_restore·createdb·dropdb를 PATH에 설치하고 별도 운영 자격 증명으로 `node server/backup-worker.mjs`를 실행합니다. BACKUP_DIR와 BACKUP_KEY_FILE로 보관 폴더와 암호화 키 경로를 지정합니다. 앱과 작업 서비스가 같은 DB를 사용해야 합니다. 작업 서비스가 없으면 관리자 화면에 연결 대기가 표시됩니다.
