# 업데이트 발행자 검증

0.8.1 이상은 설치 파일을 받기 전에 앱에 내장된 공개키로 `update-manifest.json`의 Ed25519 서명을 검증합니다. 서명된 내용은 제품·버전·소스 커밋과 각 설치 파일의 이름·크기·SHA-256입니다. URL은 고정 GitHub 저장소와 서명된 버전·파일명에서 구성합니다. 체크섬 파일도 서명된 해시와 일치해야 하며 실행 직전에 설치 파일을 다시 검증합니다. 키·버전·파일·서명이 다르거나 메타데이터가 없으면 실패로 처리합니다.

SHA-256 파일만 바꿔서는 새 설치 파일을 승인할 수 없습니다. 이 검증은 운영체제 코드 서명·Mac 공증을 대체하지 않습니다. Store 설치 앱은 기존 Windows Store 업데이트 경로를 사용합니다.

## 키와 GitHub 환경

Windows에서 저장소 루트 기준 다음 명령으로 구성하거나 동일 키를 재등록합니다.

```powershell
node desktop/scripts/setup-update-signing.mjs --register
```

- 개인 키는 채팅·로그·명령 인자로 전달하지 않고 `gh secret set`의 표준 입력으로만 등록합니다.
- `desktop-update-signing` GitHub 환경은 `main` 브랜치만 허용하며 `PM_UPDATE_SIGNING_KEY` 시크릿을 보관합니다. PR·빌드·렌더러에는 개인 키를 전달하지 않습니다.
- 개인 키 복구본은 Git 밖 Windows 사용자 전용 폴더에 DPAPI CurrentUser로 암호화해 보관합니다. 다른 사용자·PC에서는 복호화할 수 없으므로 Windows 사용자 프로필의 보호된 백업도 관리하세요.
- 앱의 `update-trust.mjs`에는 공개키만 포함합니다. 재등록은 다른 공개키를 덮어쓰거나 기존 신뢰 키를 제거하지 않습니다.
- 디버그·추적 환경에서는 키 설정을 거절하며 실패 시 외부 명령 원문을 로그에 남기지 않습니다.

## 발행과 복구

Desktop workflow에서 선택한 플랫폼의 빌드·실제 설치 검사가 성공한 뒤에만 서명합니다. 발행 작업은 검증된 커밋에 포함된 공개키와 현재 발행 코드의 공개키가 같은지 확인하고 생성한 서명을 다시 검증한 후 공개합니다. 모든 업로드의 다이제스트도 대조합니다. 키가 없거나 일치하지 않으면 공개하지 않습니다.

발행과 재공개 모두 `main`에서 실행한 원본 빌드만 허용합니다. 원본 커밋이 현재 `main` 이력에 포함되는지도 GitHub 비교 API로 검증합니다. 현재 커밋과 정상적인 과거 커밋은 허용하고, 미병합 브랜치·삭제된 이력·확인할 수 없는 응답은 거절합니다. 다른 브랜치에서 시험한 설치 파일을 공개하려면 먼저 PR을 병합한 뒤 `main`에서 다시 빌드하세요. 저장소의 `main`은 PR과 필수 CI 검사를 통해 갱신하고 강제 푸시·삭제를 제한합니다.

서명 메타데이터가 없는 과거 빌드는 새 경로로 다시 공개하지 않습니다. 새 버전으로 빌드하고 검증하세요. 이미 공개된 과거 Release는 변경하지 않습니다.

키 교체는 기존 키로 서명 가능한 동안 새 공개키를 앱에 함께 배포하는 단계부터 진행합니다. 이전 앱이 새 공개키를 신뢰하기 전에 발행 키부터 교체하면 업데이트가 거절됩니다. 키를 분실했다면 새 신뢰 키를 가진 설치 파일을 별도로 검증해 수동 설치해야 합니다. 자동으로 신뢰를 완화하는 우회 경로는 제공하지 않습니다.
